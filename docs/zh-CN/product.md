# AgentProvenance 产品方向

[English](../product.md) · 简体中文

AgentProvenance 记录 AI Agent 实际执行的操作，将应用上下文与系统遥测关联，形成可以查询、比较、回放和校验的执行证据。安全分析是其中一个使用场景。

记录涵盖状态变化、运行时事件、产物、风险信号、响应决策和审计依据。

主要流程：

```text
执行上下文
  → 接收证据
  → 执行时间线
  → 运行时因果图
  → 溯源有向无环图
  → 状态差异 / 归属查询 / 产物谱系
  → 安全分析 / 风险判定
  → 污点标记 / 响应动作
  → 回放 / 取证 / 审计清单
```

## 首次体验：下载后回放

[v0.8.2-rc.2 预发布版](releases/v0.8.2-rc.2.md)提供 Linux 和 macOS 的 amd64、arm64 命令行包。`agentprov demo` 打开本地示例首页，包含六份经过验证的签名记录和两个可选评估器指南。阅读页支持目录、图片、表格和代码复制，与 Dashboard 使用相同的视觉风格。

步骤见[快速开始](../../README.zh-CN.md#快速开始)和[示例目录](../../demo/README.zh-CN.md)。回放使用独立临时存储，不会重新执行记录中的操作。实时采集与评估器配置见各自指南。

## 适用场景

主要面向自主调用工具的 Agent，尤其是 Coding Agent：

- 追踪代码修复、重构、测试和补丁生成。
- 分析包含长工具调用链和多个子进程的自动化任务。
- 将应用上下文、系统行为、状态变化和产物关联起来，调查沙箱内的执行。
- 分析跨进程、文件、网络和沙箱边界的风险行为。
- 为审计、拒绝、终止、隔离、快照污点标记和取证导出等响应实验保留证据。飞书、钉钉等通知集成仍在规划中。
- 为重复的 Agent 或任务建立行为基线，比较偏离情况。

RL 轨迹和评估流水线也是重要的验证场景：分支展开可以检验差异比较、归属、污点和响应门禁；高并发执行可以检验记录与查询能力。

AgentProvenance 输出轨迹证据、行为偏离、运行时信号和溯源上下文。奖励、惩罚、过滤、复核和候选选择由外部评估器、训练器或任务框架决定。

## 证据分层

通常从包装已有命令开始，再按需加入内核观测和应用上下文。

### 基础记录与内核事实

```sh
agentprov record -- <agent command>
```

记录器在执行前保存工作目录状态，运行命令后计算文件差异，将变化文件保存为内容寻址产物，并记录进程和文件证据。Linux 上启用节点传感器后，可为子进程创建真实 cgroup，以 `cgroup_id` 关联整棵进程子树的内核事件，减少单靠 PID 轮询造成的遗漏。

归属依据包括：

```text
根进程 / 进程树 / 工作目录 / 时间
  / container_id / cgroup_id / 文件差异 / 产物引用
```

两种采集层次：

- **基础记录**：合成作用域标识、进程采样、文件差异。没有运行内核传感器时使用。
- **监督采集**：节点级传感器、每个作用域的真实 cgroup。用于关联该进程子树的内核事件，无需修改 Agent 框架。

系统遥测无需携带应用层 `tool_call_id`。基础记录和内核采集各自的覆盖范围应在结果中说明。

### 应用上下文

系统调用无法直接表达 Agent 身份、任务委派或工具调用意图。应用侧可补充这些信息：

- `agentprov hooks bridge` 接收框架钩子，记录 Agent 身份、`agent_spawn` 委派、`agent_message` 消息、工具调用和被拒绝的意图，例如 Claude Code 的相关上下文。
- `ai call` 或 `ai mcp` 的 `bind_scope`、`record_tool_call` 提供 `run_id`、`trajectory_id`、`execution_scope_id`、`tool_call_id`、`tool_name`、`args_hash` 等显式上下文。

上下文可用时附加到同一份执行记录，不可用时仍保留运行时证据。应用声明的来源标为 `binding_source=ai_asserted`，使用较低的默认置信值，不能改写内核事实。具体来源和数值规则见[遥测格式](telemetry-schema.md#关联语义)。

接入不依赖特定模型厂商，也不要求所有模型请求经过代理。

## 产品边界

项目负责执行溯源和证据关联，可以消费以下类别的数据或与之配合：

- Docker、OpenSandbox、gVisor、Firecracker、Kata 等运行环境。
- Kubernetes、Ray、Batch 或云调度器。
- 原生 eBPF、Falco、Tetragon、LoongCollector、auditd、包装启动器或其他运行时事件流。
- 应用跟踪系统或内部 Agent 框架事件。
- 低侵入的系统观测数据。

具体支持情况见[收尾标准](project-closeout.md)和[部署指南](amd64-kvm-k3s.md)。

```text
Agent 上下文 + 系统遥测 + 状态差异 + 产物 + 风险
  → 可查询、可回放、可审计的证据图
```

## 代码职责

```text
核心逻辑：
  record / telemetry / correlation / provenance / evidence / security /
  signals / cost / baseline / forensics

运行环境与接入：
  substrate/runtime / substrate/node / substrate/state / control /
  computerapi / ports
```

不同运行环境和采集端可以替换，关联、溯源、时间线、风险、响应、回放和审计模型继续共用。原生传感器已经实现；未来接入其他来源时，也应保持这层边界。

## 部署方式

| 方式 | 组成 | 主要使用者 |
|---|---|---|
| 仅用命令行记录 | 单个 Go 可执行文件、可选 Python 辅助包、本地 SQLite 和对象存储 | 评估任务、基准测试、CI、RL 流水线、红队测试 |
| Sidecar 或本地服务 | 服务管理存储、磁盘缓冲、关联、图查询、风险与取证 API | 沙箱和 CI 工作节点、本地安全测试 |
| 中心化证据服务，尚未实现 | 设计中的共享接收与查询、对象存储、保留策略、认证授权和界面 | 多节点调查、审计、SRE、合规和事件复盘 |

RL 和评估流水线可以只包装命令、导出记录或批次清单与 `EvalContext`。更重的遥测、常驻服务和中心化部署不应成为接入前提。详见[部署方式](deployment-modes.md)。

## 与系统观测、HIDS、OpenTelemetry 的关系

系统观测能提供进程、文件、网络和跨进程影响等事实。AgentProvenance 在其上关联应用上下文，构建运行时关系和 Git 风格的溯源图，再为分析、响应、取证和审计提供证据。

HIDS，即主机入侵检测系统，是一个有帮助的参照：沙箱中的 Agent 也需要进程、文件、网络、资源和策略监控。AgentProvenance 还记录执行、轨迹、作用域、工具调用、任务、初始状态、产物、风险、基线偏离、响应和隔离状态之间的关系。

OpenTelemetry 和 LLM 跟踪系统可以作为数据输入或输出方向。项目重点是证据谱系、差异和归属、污点传播、风险决策、响应钩子、回放与审计清单。

## 证据图应回答的问题

- 这个产物由什么操作生成？
- 执行作用域从哪个初始状态开始？
- 哪次工具调用启动了这个进程？哪个子进程产生了事件？
- 工具调用、进程、遥测、风险和响应按时间怎样展开？
- 哪个进程改变了文件？文件相对初始状态是新增、修改、删除还是未变？
- 哪种行为偏离了任务或 Agent 基线？
- 哪些外部操作被尝试、经门禁处理或被拒绝？
- 哪条执行分支被标为污染或隔离？响应门禁为何阻止继续使用？
- 风险判定和响应动作分别有哪些证据支持？
- 哪些证据和偏离信号应交给外部评估器评分？
- 这条轨迹能否在之后回看和审计？

## Git 类比的含义

| Git 风格概念 | 项目中的含义 |
|---|---|
| 作用域 | 一次执行范围 |
| 类似提交的对象 | 内容寻址证据对象 |
| 差异 | 相对初始文件状态的变化 |
| 归属 | 状态变化对应的作用域、工具调用和进程 |
| 标签 | 候选、提升、隔离或污染状态 |
| 日志 | 执行历史 |
| 回放 | 重建说明和审计清单 |

这些能力用于解释执行状态如何产生和变化，以及为什么被判为风险或不宜继续使用。回放证据不等于自动撤销现实操作，也不等于重新执行全部外部动作。
