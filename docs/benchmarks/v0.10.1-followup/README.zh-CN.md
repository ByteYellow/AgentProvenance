# v0.10.1 x86 后续修复：采集压力、WHPX 与 TLS

[English](README.md) | 中文

验收时间为 2026-11-07（北京时间），沿用已有 Ubuntu `6.8.0-139-generic` x86 虚拟机。本轮处理采集高负载丢弃、WHPX 启动警告和 TLS 覆盖缺口；长期运行、扩展内核验收、合并与发布继续暂缓。

## 高负载采集

读取器改为直接解码事件，去掉逐条反射解析和内存分配；内核缓冲读取与 JSON 输出分开执行，进程缓存按生命周期区分并限制大小。默认内核缓冲为 64 MiB，用户态队列最多保存 16,384 条记录。`--ring-buffer-mib` 可设为 1～256 之间的 2 的幂。正常停止时会先排空已接收记录，再关闭读取器。

[压力验收脚本](../../../scripts/accept_sensor_pressure.py)启动四个进程，逐项统计文件打开尝试、结果和进程退出。工作负载一结束就停止采集器，同时检查退出时的排空行为。

| 负载 | 原版结果 | 修复后结果 |
| --- | --- | --- |
| 约 0.12 秒内打开文件 4 万次 | 内核丢弃 60,428 条；停止时还有队列记录未读完 | 4 万条尝试、4 万条结果、5 条退出全部收到，零丢弃 |
| 约 17 秒内按节奏打开文件 16 万次 | 内核丢弃 33,477 条，记录不完整 | 16 万条尝试、16 万条结果、5 条退出全部收到，零丢弃 |
| 将缓冲压到 1 MiB，主动制造超载 | — | 明确报告 61,810 条丢弃，队列保持有界，正常退出 |

默认缓冲下，突发测试的传感器 RSS 峰值为 265,608 KiB，约 259 MiB。增加的内存包括更大的内核映射和用户态队列；内存较小的节点可调低缓冲预算。[完整报告](pressure.json)保留了计数、耗时和内存数据。

## WHPX 的 XSAVE 属性

剩余启动警告来自 QEMU 11.1.0 的 WHPX 初始化：读取 XSAVE 组件大小和偏移时，没有同步传递用于区分 supervisor 状态的 ECX 属性。[补丁](../../../scripts/patches/qemu-11.1-whpx-xsave-ecx.patch)补上了这一行。

本地程序由官方 QEMU 11.1.0 源码包重新编译。guest 继续使用 `-accel whpx -cpu max`，保留 CET，不添加 `nousershstk`。修复后 CPUID `0xD.11`、`0xD.12` 的 ECX 均为 `1`，启动日志中的 `misordered xstate` 警告消失。四个启用 CET 的进程各运行 120 秒，反复执行嵌套返回、CPU 迁移、让出调度和休眠，均无错误。采集器、Docker 和 K3s 服务同时保持运行。

## TLS 覆盖

- amd64 Go 1.23–1.26 的 `-s -w` 去符号程序可从 Go 函数表定位 TLS 入口，也支持 PIE。解析器限制元数据读取量；Read 继续使用返回指令处的普通 uprobe。保留符号和去符号两组程序，各有 32 个并发 goroutine，捕获字节与实际读取结果一致，栈增长和上下文清理通过。
- BoringSSL 动态库及静态链接程序均捕获到首次请求和完整响应。缺少的 `_ex` API 标为“不适用”，连接生命周期探针仍为必需项。静态 C 程序需要保留函数符号。
- 宿主机已安装的 OpenSSL 库会在采集器就绪前预挂载。新增的 `--tls-target` 可重复指定已知库或 Go 程序，启动工作负载前完成挂载，文件替换后重新检查。首次请求验收没有加入客户端启动等待。

刚出现、未提前配置的容器文件仍可能在自动挂载前发出首次 TLS 调用。未知 Go ABI、无法定位函数的 C TLS 程序需要另外适配。单次调用 4 KiB 的捕获预算保持原样，能力报告和缺口记录会继续说明这些范围。
