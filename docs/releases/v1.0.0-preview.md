# v1.0 Source Preview: Evidence Across Execution Environments

English | [中文](../zh-CN/releases/v1.0.0-preview.md)

This preview describes the current source branch, `feature/v1.0-portable-evidence`.
The published release remains v0.10.1. Existing recording, graph investigation
and signed evidence workflows remain available.

The [final x86 acceptance index](../benchmarks/v1.0-x86-completion/README.md)
records native Workspace/Browser cases, runsc fault recovery, pinned Kata/QEMU,
bounded performance and same-source Linux/macOS candidate packages with
`agentprov-verify`. The retained preview now includes a Workspace example,
input/output versions, receipts and delivery details. Formal UI integration and
publication await maintainer review; the 24-hour soak remains deferred.

## Why this version extends the evidence path

A local process tree explains work in one environment. When an Agent dispatches
to another sandbox, or reuses a browser or Notebook kernel, the investigation
needs additional context:

- **Across environments:** connect the originating Tool Call to the target's
  execution scope and result, including retries and evidence delivery.
- **Inside long-lived applications:** retain browser operations and Jupyter
  request identities, so individual actions and outputs can be inspected.
- **Across recovery and sharing:** retain instance generations, collection
  conditions and receipts, so restored tasks and exported evidence keep their history.

These additions reuse the existing Run, graph and Bundle workflows. Start with
the [sandbox deployment explanation](../deployment-modes.md#where-the-agent-and-its-tools-run)
to choose the execution entry and collector for your environment.

## Follow a Remote Tool Call

A coding agent can run on one machine while an independent command executes in
a Linux sandbox. The optional Claude command route preserves the native session
and tool-call identity, the dispatch and each execution attempt, the remote
scope, saved outputs, and signed delivery receipts.

Transport retries reuse the same attempt. An explicit reexecution creates a new
attempt. Execution, collection and delivery have separate states, so a finished
command can still have an incomplete capture or a pending receipt. Surviving
scopes can be recovered after an executor restart without rerunning the command.

Start with the [execution handoff guide](../execution-handoff.md). It covers the
trusted entry, authentication, configuration, independent commands and querying
both directions of a saved execution link.

## Keep Files and Commands in One Workspace

The optional [controlled workspace](../workspace.md) runs the entire Harness on
the machine that owns the authoritative files. Read, Edit, Write and Bash share
a workspace identity and revision. Edits use the revision or digest that informed
the change; a conflict asks the caller to reread. Bash records its observed input
and output manifests alongside the existing execution snapshot and result.

This first path uses stdio MCP and the local JSON CLI. It supports Linux and
macOS without adding a public file-execution server or synchronizing two writable
copies of a workspace.

## Record Browser and Notebook Work

Two optional application entries extend recording beyond shell commands:

| Entry | Preserved context | Saved content |
| --- | --- | --- |
| Browser | Native page, frame, operation, request, redirect and worker identities | Text, downloads, bounded screenshots and privacy-projected HAR |
| Notebook | Kernel instance, frontend session, request and parent-message identities | Cell input, output, errors and bounded static image attachments |

Both entries provide an optional MCP interface. They retain native relationship
metadata in `basic` and `detailed`; body and attachment controls determine what
is saved. A restarted kernel gets a separate identity, and late output keeps
its original request reference.

See the [Browser guide](../browser-context.md) and
[Notebook guide](../notebook-context.md) for dependencies and complete examples.
Linux system telemetry is a separate collection layer; these application entries
also work without a native sensor.

Browser operations now persist acceptance and result records. After a bridge
restart, `browser_result` reads the original operation and generation without
repeating it. Interrupted operations retain an unknown outcome. An optional
receiver-owned import verifies receipts against independently pinned capture
bytes and saves its verification separately from the original source claims.

Native references also connect operations, request lifecycles, redirect hops and
documents. An explicit receiver-owned mapping can connect a Browser context to
an observed process lifetime and its file/network evidence. These derived
relationships retain their rule and source references; selected exports recompute
them from retained support. The [Browser guide](../browser-context.md) describes
the local graph/export configuration and Linux Sensor acceptance.

## Keep Collection Conditions With the Evidence

A saved capture manifest records producer identity, collection location when
known, capability observations and changes, receive windows, loss diagnostics
and original batch receipts. Read it through the paged API or an offline export.
Unknown counts stay unknown, and selected exports retain only observations
supported by the included evidence.

This answers a practical investigation question: which collectors were active
while the task ran, and where were gaps reported? The recipient can read those
conditions alongside the events after the original sandbox has been removed.

Native Linux capture preserves passive windows through delayed Pod attribution
and spool recovery. ARM64 also uses the bounded kernel cgroup-name cache to
retain short-lived workload identity. Delayed capability notifications keep
their original timestamps while their effective intervals are clipped to the
saved receive window.

The pinned [gVisor SecCheck entry](../gvisor-seccheck.md) observes Sentry events
with separate sandbox and lifecycle identities. Its checkpoint/restore workflow
uses external registration and signing authority to distinguish resumed and
cloned instances. The [Firecracker guest recipe](../execution-handoff.md#guest-service-and-image)
provides image/kernel builders and automatic collection/sealing services.
The amd64 profile has passed actual boot, signed delivery and receipt-gated
retirement; see the [runtime and performance results](../benchmarks/v1.0-amd64/README.md).

The [runtime adapter guide](../runtime-adapters.md) adds explicit native, Guest
and fixed-container runsc configuration. Guest bindings carry the platform's
Pod/container and boot identity. runsc binds commands to exact Sentry process
lifetimes and descendants, waits for a durable completion marker, and includes
the original command evidence in signed delivery. Its [x86 fault matrix](../benchmarks/v1.0-x86-completion/runsc-execution.json)
covers lost replies, retries, cancellation and receiver/executor restarts.
The fixed Kata/QEMU combination has passed its nine R-03 checks; see its
[result and version lock](../benchmarks/v1.0-x86-completion/README.md) and
[reproduction procedure](../validation/kata-qemu.md).

## Share a Bounded Investigation

Select multiple Runs with `dashboard export --selection-file`, or share a single
session with `--harness` and `--session`. Each selection retains its own evidence
boundary. The exported directory includes saved bodies, graph views, search and
capture observations and opens through `file://` without the original database.

The CLI now provides three [delivery modes](../derived-evidence.md): an unsigned
reading copy, a selected reader signed by its exporter, or complete originals
with their original producer signatures. Complete-original mode requires a whole
Run, an explicitly selected registered bundle and confirmation of its full scope.
Selected or redacted readers do not attach excluded originals.

Use the independent `agentprov-verify` command with the recipient's external key
and role policy. It reports file integrity, original and exporter signatures,
trust and capture coverage separately. Dashboard controls for these modes remain
in local preview. Browser and Notebook attachments stay inert; the reader never
executes saved commands or automatically loads remote evidence resources.

## Choose an Example

The [example guide](../demo-library.md) groups task investigation, cross-sandbox
collaboration and non-coding work, with specialized and historical cases kept
separately. Fresh captures use new Run IDs and signatures. Grok remains a dated
historical recording; its original packages and links are retained.

The new execution details and attachment readers remain a
[rebuildable local preview](../../previews/v1.0-reader/README.md), with task
investigation, cross-environment execution, Workspace, Browser and Notebook entries.
The [example guide](../demo-library.md#read-the-v10-candidate-examples) explains
the story, evidence path and recording type for each entry. These readers await
formal integration; the released Dashboard retains its existing layout.

Before trying the source build, back up the data directory. An upgraded database
must be used with its matching or newer binary. Optional entries require the
dependencies described in their guides; they are not enabled by installing the CLI.
